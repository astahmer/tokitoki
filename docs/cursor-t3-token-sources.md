# Cursor / T3 Code token sources

Research checked 2026-10-26. Scope: public first-party documentation, pinned public T3 source, this checkout's adapters, and installed application **code only**. No credentials, private messages, live provider requests, databases, or configuration were read or changed. This note is research for implementation; it does not claim the recommendations are implemented.

## Answer and implementation priorities

Yes: Cursor account usage and supported T3 V2 providers expose reported token counts. `chars / 4` is a fallback estimate of visible text, not measured model usage. Availability depends on source, build, provider, and turn status. Three immediate implementation concerns:

1. **Normalize T3 input before pricing:** T3 `turnTokenUsage.inputTokens` includes cached reads and writes. Tokitoki's `TokenCounts.inputTokens` is uncached input. Subtract known cache buckets once; preserve unknown buckets as unknown. Output already includes reasoning; do not add reasoning again.
2. **Do not use an append-only rowid cursor for mutable turns:** T3 upserts a running provider-turn row when it completes. Advancing past it before usage arrives can permanently miss its final counts. Revisit pending IDs, or rescan/upsert terminal rows with stable IDs and an overlap/update mechanism.
3. **Keep T3 excluded from account totals**, including when its tokens are reported. Cursor account usage covers overlapping application activity; native harness readers cover the other providers. Reported T3 activity is useful for session detail, not an additional bill.

These follow from the [T3 token contract](https://github.com/pingdotgg/t3code/blob/bfc7177f9f54b0a4b9d3571d30723a51cd4b31bd/packages/contracts/src/providerRuntime.ts#L322-L344), [provider-turn upsert](https://github.com/pingdotgg/t3code/blob/bfc7177f9f54b0a4b9d3571d30723a51cd4b31bd/apps/server/src/orchestration-v2/ProjectionStore.ts#L2450-L2505), and local [pricing contract](../src/pricing.ts), [T3 importer](../src/providers/t3code.ts), and [totals exclusion](../src/cache.ts).

## T3 normalization, provider by provider

The common `TurnTokenUsage` contract has `usageScope: "main_agent"`, `hasSubagents`, and `usageStatus: "complete" | "partial" | "unavailable"`. Complete requires input and output; partial/unavailable can omit them. Cache and reasoning counters remain optional even for complete. The source explicitly says input includes cache reads/writes and output includes the reasoning subset. A complete **main-agent** turn is not proof of complete parent-plus-subagent account usage. See [contract](https://github.com/pingdotgg/t3code/blob/bfc7177f9f54b0a4b9d3571d30723a51cd4b31bd/packages/contracts/src/providerRuntime.ts#L322-L344).

- **Codex:** accumulates differences of thread-wide `total` counters over a live turn; uses `last` on first observation or counter reset. Late finished-turn observations update the baseline without adding to the live turn. Input is already inclusive of cache reads/writes. Read/write counts are clamped individually to input; reasoning to output. Cache creation becomes unknown when a delta cannot provide it. No observed positive usage produces unavailable; completed produces complete, other terminal states partial. This is a sum across model responses in a turn, not the latest context size. [Normalizer](https://github.com/pingdotgg/t3code/blob/bfc7177f9f54b0a4b9d3571d30723a51cd4b31bd/apps/server/src/provider/CodexTurnTokenUsage.ts).
- **Claude Agent:** consumes SDK result `usage`, adding earlier steering-aborted segment results. Native `input_tokens` is uncached; T3 adds `cache_read_input_tokens` and `cache_creation_input_tokens` to make inclusive input. Missing/null native cache fields contribute zero to the input sum, while absent optional cache fields remain omitted. Invalid supplied cache counts can make input unknown. Output is native `output_tokens`; optional thinking is clamped to output. Successful completed result with known input/output is complete; known partial usage is partial; absent usage, or a non-success result with no positive usage, is unavailable. [Normalizer](https://github.com/pingdotgg/t3code/blob/bfc7177f9f54b0a4b9d3571d30723a51cd4b31bd/apps/server/src/provider/ClaudeTurnTokenUsage.ts).
- **OpenCode SDK adapter:** sums unique owned step-finish parts. Input = `tokens.input + tokens.cache.read + tokens.cache.write`; output = `tokens.output + tokens.reasoning`. Stores cache and reasoning separately as subsets of those inclusive sums. Ownership resolution and unresolved steps can force partial. No observed step parts yields unavailable. [Accumulator](https://github.com/pingdotgg/t3code/blob/bfc7177f9f54b0a4b9d3571d30723a51cd4b31bd/packages/provider-opencode/src/server/adapter.ts#L215-L256), [terminal status](https://github.com/pingdotgg/t3code/blob/bfc7177f9f54b0a4b9d3571d30723a51cd4b31bd/packages/provider-opencode/src/server/adapter.ts#L1110-L1143).
- **OpenCode V2:** sums step-ended/step-failed counters with the same inclusive input and output formulas. Zero steps yields unavailable; completed terminal turn yields complete, otherwise partial. Its separate latest-step `tokenUsage` has different context-display semantics. [Terminal normalization](https://github.com/pingdotgg/t3code/blob/bfc7177f9f54b0a4b9d3571d30723a51cd4b31bd/packages/provider-opencode/src/server/v2/adapter.ts#L631-L647), [step accumulation](https://github.com/pingdotgg/t3code/blob/bfc7177f9f54b0a4b9d3571d30723a51cd4b31bd/packages/provider-opencode/src/server/v2/adapter.ts#L2103-L2114).
- **Cursor, installed custom build:** `cursorTurnTokenUsage` validates four nonnegative integer raw buckets (`inputTokens`, `outputTokens`, `cacheReadTokens`, `cacheWriteTokens`); optional reasoning must not exceed output. Normalized input = raw input + cache read + cache write. Output is copied. Completed with no missing usage is complete; other known usage partial; invalid/missing usage unavailable. It emits this on terminal provider-turn updates. This comes from the local bundle's `turn-usage.ts` region, not checked public main. **Public main's Cursor adapter has no `turnTokenUsage` emission** at this revision, so do not promise actual Cursor per-turn projection counts across all T3 installs. [Public adapter for comparison](https://github.com/pingdotgg/t3code/blob/bfc7177f9f54b0a4b9d3571d30723a51cd4b31bd/packages/provider-cursor/src/server/adapter.ts).
- **Muse:** streaming `session/tokenUsage` accumulates input from `promptTokens`, output/cache/reasoning from event usage, and marks partial. Terminal `turn/completed` with usage marks complete, retaining accumulated input if present, replacing output with terminal output, copying cache read (or legacy `cachedTokens`), reasoning, and optional cache write. No extra cache addition or reasoning addition occurs here. The generic inclusive contract is the intended interpretation, but the adapter alone does not prove the upstream protocol's accounting; validate invariants and do not silently repair conflicting values. [Adapter](https://github.com/pingdotgg/t3code/blob/bfc7177f9f54b0a4b9d3571d30723a51cd4b31bd/packages/provider-muse/src/server/adapter.ts#L1437-L1518), [protocol](https://github.com/pingdotgg/t3code/blob/bfc7177f9f54b0a4b9d3571d30723a51cd4b31bd/packages/provider-muse/src/server/protocol.ts#L6-L13).
- **Pi, Grok, Antigravity / generic ACP registry drivers:** no normalized per-turn `turnTokenUsage` producer was found in their checked adapters. Pi can expose separate session/context snapshots; Grok and Pi have native history usage readers; these are not proof that the T3 turn projection has actual usage. Read those native sources for account totals where supported, and show absent T3 turn counts as unavailable. [Pi adapter](https://github.com/pingdotgg/t3code/blob/bfc7177f9f54b0a4b9d3571d30723a51cd4b31bd/packages/provider-pi/src/server/adapter.ts), [Grok adapter](https://github.com/pingdotgg/t3code/blob/bfc7177f9f54b0a4b9d3571d30723a51cd4b31bd/packages/provider-grok/src/server/adapter.ts), [generic ACP adapter](https://github.com/pingdotgg/t3code/blob/bfc7177f9f54b0a4b9d3571d30723a51cd4b31bd/packages/provider-acp/src/server/adapter.ts), [Grok history parser](https://github.com/pingdotgg/t3code/blob/bfc7177f9f54b0a4b9d3571d30723a51cd4b31bd/packages/provider-grok/src/server/usage.ts).

The local importer currently selects V2 when `statev2.sqlite` exists, reads only completed turns, skips unavailable, maps absent fields to zero, and copies inclusive input unchanged alongside cache buckets. It loses partial/missing-field fidelity and can miss updates because of the rowid watermark. Its V1 path uses the preceding user text plus assistant text divided by four; it does not recover hidden context or model calls. These observations describe the working-tree snapshot during research, not an immutable Tokitoki release. [Local adapter](../src/providers/t3code.ts).

## Cursor account source and import wiring

Cursor's documented Admin API `POST https://api.cursor.com/teams/filtered-usage-events` exposes event `tokenUsage` with input, output, cache read/write and model cost, when `isTokenBasedCall` is true. Request-based events can lack it. This is a team/admin credential API, distinct from the logged-in personal dashboard route. The current docs describe hourly aggregation and recommend polling at most hourly; do not call it a real-time stream. [Official Admin API](https://cursor.com/docs/account/teams/admin-api).

The official team analytics docs confirm CSV downloads of visible chart data and all-chart downloads from the page header; they describe analytics API access as Enterprise-only. This confirms an export option, but does **not** establish that every analytics CSV is a billing-event token CSV, or guarantee a stable token-column schema. Validate headers from an explicitly supplied billing export before implementing CSV import; never interpret accepted lines, requests, or chat counts as tokens. [Official analytics and CSV documentation](https://cursor.com/docs/account/teams/analytics#csv-download).

The current API overview lists Admin/Analytics API availability for Enterprise teams; do not promise personal-plan or general Teams-plan API access. Official web release notes separately describe filtered event-level Usage exports for pooled organizations, with export disabled for some organization configurations. The checked docs do not specify a stable complete billing CSV column contract. [API availability](https://cursor.com/docs/api), [web release notes](https://cursor.com/docs/release-notes/web). For billing reconciliation, Admin API docs recommend summing `chargedCents`, which includes applicable Cursor Token Rate fees; `tokenUsage.totalCents` represents model cost and is not necessarily the final charge. [Cost reconciliation](https://cursor.com/docs/account/teams/admin-api).

T3's public account reader uses `https://cursor.com/api/dashboard/get-filtered-usage-events`, receiving `usageEventsDisplay`; its conversion explicitly calls raw `inputTokens` **uncached**, then maps cache read/write separately. It skips missing `tokenUsage`, validates supplied numeric fields, defaults omitted fields to zero, maps optional `conversationId`, converts cents to dollars without integer truncation, and handles page-boundary duplicates. This is strong first-party implementation evidence for the dashboard's bucket semantics, but the route is an internal web endpoint, not a documented supported public API. [Endpoint and reader](https://github.com/pingdotgg/t3code/blob/bfc7177f9f54b0a4b9d3571d30723a51cd4b31bd/packages/provider-cursor/src/server/accountUsage.ts#L94-L100), [normalization](https://github.com/pingdotgg/t3code/blob/bfc7177f9f54b0a4b9d3571d30723a51cd4b31bd/packages/provider-cursor/src/server/accountUsage.ts#L283-L326).

Tokitoki already imports the dashboard via [cursor-dashboard.ts](../src/providers/cursor-dashboard.ts). [pollCursorQuotas](../src/poll.ts) calls `syncCursorDashboardUsage` before fetching quota windows. It reuses the existing local CLI/IDE login; dashboard failure is caught so quota polling can continue. The dashboard importer constructs the WorkOS session cookie locally, rejects redirects, requests 1,000 rows/page up to 40 pages, starts with a 90-day window, overlaps by one hour, appends events, and inserts into cache. It saves its own watermark only after a successful pass. This research did not execute it.

Manual `tokitoki poll` triggers that path; automatic polling is opt-in via `[poll].enabled`, normally 15 minutes with `[poll].intervalMinutes` controlling cadence. `tokitoki poll --enable` enables background polling. Merely scanning local SQLite does not trigger dashboard import. See [config](../src/config.ts), [CLI](../src/cli.ts), [poll integration](../src/poll.ts). Do not confuse the existing private-dashboard cadence with the documented Admin API's hourly recommendation.

Importer limitations to resolve or communicate: missing bucket fields currently become zero; `totalCents` incorrectly shares an integer-truncating token parser and can lose fractional cents; a fully populated 40th page needs an explicit incomplete state; per-page occurrence indices need boundary/overlap-aware handling; the watermark is global rather than account-specific. Local IDE bubble estimates use the same `cursor` provider/account but different event IDs, so importing actual dashboard rows does not itself deduplicate old estimates. Source-aware replacement/exclusion is needed before claiming account totals are wholly reported. [Dashboard importer](../src/providers/cursor-dashboard.ts), [local bubble scanner](../src/providers/cursor.ts).

## Recommended source and fallback contract

- Prefer provider/account reported billing events for account totals: Cursor dashboard today; documented Admin API or explicit CSV import when authorized/available. Keep the acquisition source and coverage window visible. Do not infer a token count from request units or spend percentages.
- For T3 session detail, use validated V2 `turnTokenUsage`; preserve `complete`, `partial`, `unavailable`, `usageScope`, subagent presence, and optional counters. Do not reinterpret `tokenUsage.usedTokens` or context-window percentages as cumulative billed tokens. Include failed/interrupted terminal turns as partial activity when they carry usage.
- Canonical token buckets should be disjoint: uncached input, cache read, cache creation, inclusive output; reasoning is an optional output subset. For T3 known cache buckets, `uncached = inclusiveInput - cacheRead - cacheCreation`. Reject/flag negative results and inconsistent subset counts rather than silently manufacturing usage. If a cache bucket is unknown, preserve inclusive input and unknown allocation separately: total processed input can be reported even when exact pricing allocation is unavailable.
- Token provenance and price provenance are independent: reported tokens can have estimated or unknown cost. A successful request can report zero cost; missing cost is not zero. Keep decimal money precision.
- Retain missing/partial values as unknown or partial; zero means an observed or source-defined zero. Count coverage explicitly (for example, “12 reported turns, 3 without usage”). Do not make a complete-looking zero row out of absent usage.
- Retain estimates only with explicit provenance such as `estimated_chars`, a clean `≈` prefix and “Estimated from visible text” detail. Mixed aggregates should say “Includes estimates” with reported/estimated coverage. Unknown usage should display `—` / “Unavailable”, not `≈0`. Estimated cost must be marked separately. A tokenizer fallback can improve counting of visible text, but remains an estimate of billed usage.
- Source selection must prevent overlaps: dashboard/native account sources win over overlapping local message estimates; all T3 rows remain activity-only and excluded from account totals, rollups, budgets, and account token/cost summaries. Do not remove the existing `provider <> 't3code'` safeguard.

## Why characters divided by four is not measured usage

Implementation follow-through: token provenance now survives storage and
session detail, with separate token/cost labels in QML, Swift and web. Cursor
dashboard events are reported account usage; local bubble estimates remain
activity-only. T3 V2 normalizes inclusive input, revisits pending mutable turns,
and exposes token provenance on its separate activity reports. V1 retains a
labelled visible-text estimate. Fractional cents are retained, while legacy
Cursor event ID rounding is kept solely for replay compatibility. The dashboard
watermark remains global and page-boundary reconciliation remains a limitation;
this work does not claim a documented public personal-account API.

OpenAI describes approximately four characters per token as an **English** rule of thumb, with tokenization depending on model, encoding, and language. The current article explicitly says plain-text counting can omit message structure, tools, schemas, images, and files. The API response's usage counters are the source for actual processed usage; visible text alone cannot reveal model context, cache billing, tool results, repeated model calls, hidden instructions, or reasoning. [Official OpenAI token explanation](https://help.openai.com/en/articles/4936856-understanding-and-counting-tokens).

For code specifically, punctuation, indentation, identifiers, and model-specific encodings break any universal characters-to-token ratio. OpenAI's own `tiktoken` examples show different encodings and different token counts for identical text, including arithmetic and Japanese. Thus a tokenizer for the correct model is preferable for a **text-length estimate**, but is still not a replacement for provider usage over the actual complete request. [OpenAI tokenizer cookbook](https://cookbook.openai.com/examples/how_to_count_tokens_with_tiktoken), [official tokenizer implementation](https://github.com/openai/tiktoken).
